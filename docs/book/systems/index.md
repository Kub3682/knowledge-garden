# 第四篇 · 怎样让计算适应更大的任务

上一篇，教学机已经能按程序处理数据。输入 2 和 3，执行取数、相加、保存，最后得到 5。

可要处理一万条记录，结果正确还不够。今晚能算完吗？电池够不够？为了快一点，多放部件值不值得？

问题从“能不能执行”，走到了“怎样执行才合适”。这一篇先建立观察硬件的办法，再逐步走向并行与异构计算。

## 同一条指令，为何快慢不同？

先把上一篇的 `ADD 5` 看得再近一些。

它规定，把地址 5 的数加到 ACC，结果仍放入 ACC。这个约定并未规定，机器内部要用几个时钟周期，也未规定存储器距离运算部件有多远。

一种实现可能分几次取数、运算和保存，复用同一套通路。另一种可以安排更多部件，让部分准备工作同时进行。它们要提供相同的指令行为，内部用时与成本却可能不同。

这种让指令实际运行起来的内部组织，叫**微架构**。寄存器怎样连接，运算部件怎样安排，指令怎样调度，缓存放在哪里，都属于它关心的内容。

| 观察什么 | 要回答什么 |
| --- | --- |
| 指令集 | 执行这条指令，应发生什么 |
| 微架构 | 用什么内部安排，完成这个行为 |
| 工艺与电路实现 | 怎样制造部件，并让它们可靠工作 |

## 时间花在了哪里？

还是那道加法，等数、相加、保存，哪一步慢，就会影响完成时间。加法器即使很快，数还没送到，也只能等。

若连续处理很多条记录，还得问，能否在处理这一条时，准备下一条？若这一步必须等前一步的结果，又能否先做别的？

因此，研究性能时要分清两种需要。**延迟**关心一件事多久完成，**吞吐量**关心一段时间能完成多少件事。

比如，把取数、运算、保存安排成不同阶段。第一条进入运算时，第二条可以开始取数。阶段之间能够衔接，就像工序接力，这叫流水线。它有机会提高连续任务的吞吐量，一条任务从头走到尾的时间却未必缩短。

若后一条马上要用前一条的结果，或两条争用同一部件，衔接便会受阻。快慢来自具体的数据关系与资源安排，不能只数阶段有多少。

## 哪些工作可以同时做？

先比较两份很短的工作单。

<div class="dependency-pair" role="group" aria-label="比较有依赖和相互独立的加法">
  <div><strong>要等上一步</strong><code>a = 2 + 3</code><code>b = a + 4</code><small>算 b 前，要先得到 a</small></div>
  <div><strong>可以分开做</strong><code>a = 2 + 3</code><code>b = 7 + 4</code><small>两个结果互不依赖</small></div>
</div>

前一种，即使多放一个加法器，b 也得先等 a。后一种，只要部件和数据供给够，便有机会同时算。

这就是并行的一个前提，先找到可以同时推进的工作。任务的依赖关系，会限制硬件能够发挥的空间。

再把问题放大。若有一千组数，每组都作同样的加法，就可以让一条操作带动多条数据通道，这种方式叫 **SIMD，单指令多数据**。若有多份能独立推进的任务，也可以交给多个 CPU 核心分别执行。

两者还能组合。一个多核 CPU 的每个核心，都可能有 SIMD 能力。它们分别回答怎样分配任务、怎样让同一种操作覆盖多个数据。

## 数总要从远处搬来吗？

并行的部件多了，需要的数也更多。供给跟不上，部件就会空等。

还拿记录举例。若一小段数据会反复使用，每次都去很远的存储位置取，便白白增加搬运。把近期会用到的副本留在近处，就有机会减少这类等待。这是引入缓存、安排数据复用的重要理由。

近处的存储通常容量有限。哪些数据放得下、能复用几次、访问是否有规律，都会影响效果。光看运算部件每秒能算多少次，无法判断整个任务能跑多快。

Roofline 模型把这种制约画成了清楚的性能上界，同时看计算峰值、所考察存储层的带宽，以及每搬运一定数据能完成多少运算。这里先抓住一句话，**运算能力需要数据供给来兑现**。需要公式与图表时，可读[伯克利实验室的模型介绍](https://amcr.lbl.gov/departments/computer-science-department/ppan/roofline-performance-model/)。

## 交给专用部件，就一定快吗？

有些任务结构稳定，同样的运算要反复做。为它配置合适的运算单元、数据通路和局部存储，可能比通用执行更有效。DSP、GPU、NPU 与数据流加速器各自有这样的设计背景。

不过，交出去也要花时间。准备任务、提交、等待、把输入送过去、把结果取回来，都可能计入一次任务的完成时间。

先用一个小实验看这种取舍。这里假设，加速器每项运算只花 CPU 的四分之一，但每次启用它，都要额外付出固定的提交和搬运时间。

<OffloadCost />

一次只算一项，快一点的运算，可能抵不过交接成本。攒成一批，固定成本摊开，加速才显出好处。实际系统还可能重叠搬运与运算，或让数据长期留在设备上，比较时要按实际路径测量。

“模型很小，应该用哪种芯片”，单凭模型大小仍无法作答。还要看它做哪些操作，中间数据多大，多久来一次输入，以及必须多快给出结果。

## 不同计算方式从哪里来？

到这里，再整理 CPU、SIMD、GPU、NPU 这些名称，便有了一把比较的尺子。

先问任务。操作是否相同？数据能否分组？下一步依赖谁？哪些数会反复用？数值需要多精确？然后问约束。一次响应要多快，持续处理要多快，能用多少电、多少面积和多少成本？

这些条件共同影响硬件设计。控制工作如何分配，数据如何流动，状态保存在哪里，是其中三条重要线索。

| 设计线索 | 需要作出的取舍 |
| --- | --- |
| 控制 | 每个任务多灵活，多少操作能共享一次调度 |
| 数据 | 哪些工作并行，数据按什么顺序到达 |
| 存储 | 状态放在哪里，怎样减少重复搬运 |

不同名称并不都处于同一层次。CPU 是处理器类别，SIMD 是执行方式，GPU 和 NPU 也仍需要指令或其他控制机制。它们可以共存，并按任务协作。

**计算的本质仍是按规则变换信息状态。不同硬件设计的分歧，在于怎样组织这种变换，才能满足具体任务的时间、能耗、成本与灵活性要求。**

因此，演进会分叉，也会组合。通用处理器承担多变的工作，专用部件承担结构稳定的工作，二者之间还要算清协调与搬运的账。

<details class="reading-note">
<summary>物理边界 · 为什么计算还有能量成本？</summary>

状态最终要由实际物理系统承载，改变和保存状态都要服从物理规律。兰道尔原理讨论其中一个特定边界，在标准的等温擦除情形下，把一个未知、0 与 1 等概率的比特复位为确定值，环境平均至少接收 kBT ln 2 的热量。这里 kB 是玻尔兹曼常数，T 是环境的绝对温度。

这一下界针对逻辑不可逆的信息擦除。估算处理器执行一次加法的能耗，还需要具体电路与工作条件。在本篇的硬件比较中，控制、运算和数据搬运都要纳入实际测量。[Landauer，1961 年论文](https://doi.org/10.1147/rd.53.0183)

</details>
